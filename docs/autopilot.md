# 自動改善の手順（AI が毎日・毎週自分で回す）

運営者が 2026-11-12 に決めた仕組み。スケジュールタスクが新しいセッションでこのファイルを読み、書いてあるとおりに動く。
運営者は週1回のレポートを見て、まずいものだけ止める。**運営者への確認待ちで作業を止めない。** 承認が要るものは PR にして先へ進む。

## 0. 毎回の準備
1. リポジトリを最新にする（`git pull`）。作業環境に前の回の履歴が残っていて `git pull` が「履歴が食い違っている」と止まるときは、手元の `main` を別の名前のブランチに退避してから `git fetch origin && git reset --hard origin/main` で公開中の `main` に合わせる（2026-11-16 の週次の回で起きた）。
2. 次を読む：`CLAUDE.md` → `docs/STATUS.md` → `docs/goals.md` → `ops/metrics/latest.md` → `docs/experiments.md` → `docs/backlog.md`。
3. `ops/metrics/latest.md` の日付が今日でなければ、`python3 ops/metrics.py` を自分で動かす（Search Console の取得が止まっていれば、それも報告に書く）。
4. `seo/gsc/api/by_date.csv` の新しい3日分の表示回数を見る。3日続けて0回なら、その日の報告と `docs/STATUS.md` に書く（2026-11-09 から0回が続いていたのに、11/16 の週次の回まで誰も気づかなかったため）。

### Fable は使わない（2026-11-18〜）
Claude Fable は追加のクレジットがないと使えなくなり、11/18 の毎日の回はそのせいで動かずに止まった。運営者から指示があるまで、スケジュールタスクは Claude Opus で動かし、サブエージェントも `model: "fable"` では呼ばない。深い分析・仮説出し・外の調査は自分で行うか、`model: "opus"` のサブエージェントを使う。

## 1. 自動で進めてよい範囲と、承認が要る範囲

| 自動でマージしてよい | 承認が要る（PR を作り、タイトルの先頭に【承認待ち】を付けて止める） |
|---|---|
| バグの修正 | デザインの大きな変更（色・レイアウトの作り替え） |
| 収集元の追加・読み取りの改善 | 広告の場所・形式 |
| タイトル・説明文・内部リンクの改善（SEO 担当のルールに合うもの） | お金がかかるもの（有料の API・サービス） |
| 表示速度・生成の速さの改善 | 外部サービスへの登録・アカウント作成・SNS への投稿 |
| 検査・計測の追加 | データの削除、口コミ・報告の表示ルールの変更 |
| 文書（`docs/`・`ops/`）の更新 | （読み物の記事・クイズは、画像も含めて自動でよい。2026-11-18 に運営者が「画像は AI が都度入れてよい」とした） |
| | `docs/goals.md`・`ops/goals.json`・このファイルの「自動でよい範囲」を広げる変更 |
| | `CLAUDE.md` の決まりと食い違う変更 |

迷ったら承認待ちにする。

### 上限
- 自動マージは1日1件まで。
- サイトマップに載るページを、1回の変更で100件以上増やさない。テンプレートの文言だけが違うページを大量に作らない（Google の「大量生成コンテンツ」の扱いを受ける危険がある）。
- 受付サーバー（`worker/`）の変更は、`worker/` のテストをすべて通したものだけ。
- `check` が合格していない PR はマージしない。GitHub のルールセットで壁にすることも試したが、個人のリポジトリでは GitHub Actions（データの保存）を例外にできず、入れると保存が止まるのでやめた（2026-11-17）。代わりに `gate` ワークフローが、main に入った PR の `check` の結果を毎回確かめ、合格していなければ失敗してメールが届く。`gate` が失敗したら、その日は新しい改善をせず、該当の PR を元に戻すか `check` を通して確かめる。

### 使用量の上限（2026-11-17〜）
運営者は同じプランを、本業と、ほかのスケジュールタスク（毎朝の業界定点観測、週1の副業の進捗チェック）にも使う。自動改善の回は、これまで1回3〜7分で終わっている（11/16 の週次は約7分、11/17 の毎日は約4分）。
下の上限は暴走を止めるための柵で、ふだんの回が当たる高さにはしていない。上限に当たったら、その日はそこで止めて、残りを次の回に回す。

| 項目 | 上限 | 当たったら |
|---|---|---|
| Opus のサブエージェント（深い分析用。Fable は使わない） | 毎日の回は1回まで、週次の回は3回まで | 自分で考えて進める。足りなければ backlog に「深く調べる」と書き、次の回に回す |
| 検証役のサブエージェント（下の 2 の 5） | 1つの PR に1回まで。`model: "sonnet"` で呼ぶ | 不合格なら直すのは1回まで。2回目も不合格なら PR を閉じる |
| `check` の不合格を直す | 1つの PR で2回まで | PR を閉じ、backlog にわけを書く |
| 同じ失敗が2回続いた（エラーの文が同じ） | その場で止める | 試したことを backlog と STATUS に書く。3回目は試さない |
| `check` の結果待ち | 5分おきに見て、合計30分まで | PR を開いたままにし、翌日の回の最初に片付ける |
| 1回の作業の長さ | 目安45分 | 途中までを PR か backlog に残して終える |

### 失敗したときの分け方
「失敗したからもう一度」はしない。先に、どの種類の失敗かを決める。
- 時間切れ・GitHub 側の一時的な不調（HTTP 5xx、パッケージ取得の失敗）→ 1回だけ、少しあけてやり直す
- コマンドや API の使い方の誤り → 呼び方を直す（やり直しは1回まで）
- 情報が足りない → 調べに行く（推測で埋めない）
- 検査（テスト・`verify.js`）の不合格 → **コードを直す。テストや検査を消す・ゆるめる・飛ばすことはしない**
- 権限で断られた（ブランチの削除など）→ 運営者の手作業として STATUS の4章に書く
- 同じ失敗が2回 → 止める（上の表）

## 2. 毎日の改善（1日1回）
1. **守る数字を見る。** `ops/metrics/latest.md` の「守る数字の警告」があれば、その日は新しい改善をしない。原因を調べて直す。直近の自動マージが原因なら `git revert` の PR を作ってマージする。
2. **判定日が来た実験を判定する。** `docs/experiments.md` で判定日が今日以前のものを、書いてある数字で判定する。
   - 効いた → 結果を「採用」にする
   - 効かない・悪化した → 自動マージしたものは元に戻し、結果を「不採用」にして理由を書く
   - データが足りない → 判定日を1週間延ばす（延ばすのは2回まで。その後は「判定不能」）
   - 学んだことを「わかったこと」に1行足す
3. **今日やることを1つ選ぶ。** `docs/backlog.md` から、今の段階（または D）に効き、「自動」で、点数がいちばん高いものを選ぶ。
   - 良い候補がなければ、データから新しい仮説を3つ立てる。**1つは、これまでの実験と違う方向にする。** 点数を付けて backlog に足し、そこから選ぶ。
   - `docs/experiments.md` の「わかったこと」で効かないとわかった型は選ばない。
4. **完了の条件を先に書く。** 作り始める前に、PR の本文の先頭に次の4行を書く（記事「ハーネス」の考え方。2026-11-17 に取り入れた）。
   ```
   目的：（どの段階・どの数字のためか）
   変えないこと：（触らないファイル・決まり）
   完了の条件：（手元で通すコマンド、check の合格、判定日にどの数字がどう動けばよいか）
   行き詰まったら：推測で進めず、試したことを backlog に書いて止める
   ```
   「完了の条件」が書けないものは、まだ作らない（backlog に戻して点数を下げる）。
5. **小さく作る。** ブランチは `auto/YYYY-MM-DD-<短い名前>`。差分は300行くらいまで。
   - ページの追加・タイトルの変更・URL の変更は、`.claude/agents/seo.md` の判断ルールに照らす（SEO 担当のサブエージェントが使えれば呼ぶ）。
   - 手元の検査：`worker/` を触ったら `worker/*.test.mjs`。サイトを触ったら `cd site && python3 build.py`（生成）が通ることを確かめる。作業環境ではブラウザの検査（`verify.js`）が動かないことがあるので、ブラウザの検査は次の GitHub の `check` に任せる。
   - GitHub の検査：PR を作ると `check` ワークフロー（`.github/workflows/check.yml`。生成＋`verify.js`）が動く。1回20〜30分。結果は `gh api repos/nekolab0/kaji23/commits/<ブランチの最新コミット>/check-runs` で見る。不合格なら直す（上限は「使用量の上限」の表）。直せなければ PR を閉じ、backlog にわけを書く。`.md`・`docs/`・`ops/`・`data/`・`verify/`・`seo/` だけの変更でも `check` は動くが、重い検査は飛ばして1分ほどで合格になる。
6. **作った人とは別の目で確かめる（検証役）。** `check` が合格した自動の PR は、マージの前に、Agent ツールのサブエージェントを `model: "sonnet"` で1回呼び、次の文を渡す（文書・データだけの PR は飛ばしてよい）。自分で書いた変更を自分で見直すと、同じ思い込みのまま「よさそう」と判断しがちなので、役を分ける。
   ```
   あなたは検証役です。この変更を書いていません。仕事は、マージしてはいけない理由を探すことです。
   材料：PR の本文（完了の条件）、差分（gh api repos/nekolab0/kaji23/pulls/<番号>/files）、check の結果、リポジトリの CLAUDE.md と docs/autopilot.md の表。
   順に確かめる：
   1. 「完了の条件」の各行に証拠があるか。証拠がない行があれば不合格。
   2. 差分が「変えないこと」や、docs/autopilot.md の「承認が要る」範囲に触れていないか。
   3. テスト・検査を消した・飛ばした・ゆるめた跡がないか。
   4. 火事の場所・時刻・件数を間違えて出す入力の例を1つ考え、その場合にどうなるかを確かめる。
   答えは次のどちらか1つだけ：
   不合格：<満たしていない条件と、その証拠>
   合格：<条件ごとに1行、その証拠>
   ```
   不合格なら直して `check` からやり直す（1回まで）。2回目も不合格なら PR を閉じ、backlog にわけを書く。
7. **出す。**
   - 自動の範囲：`check` が合格し、検証役が合格と答えたら PR をマージする（`gh api -X PUT repos/nekolab0/kaji23/pulls/<番号>/merge -f merge_method=squash`）。マージで動く `daily` の公開が成功したかを確かめ、失敗したら元に戻す。セッションの残り時間で `check` が終わらないときは、PR を開いたままにし、翌日の回の最初にマージする。
   - 承認が要る：PR を作って止める。週次レポートに載せる。
8. **記録する（同じ PR に入れる）。**
   - `docs/experiments.md` に1行（何を・なぜ・どの数字がいつまでにどう動くはずか・判定日）。判定日は、インデックス・検索の数字なら14日後、速さ・件数なら3日後が目安。
   - `docs/backlog.md` の該当の行を「実施中」にする。
   - `docs/STATUS.md` を更新する。大きな判断は `docs/decisions.md` にも書く。
   - **バグを直したときは、同じ種類の失敗をもう一度起こさない仕組みを1つ残す。** 強い順に、検査で止める（`verify.js`・`worker/*.test.mjs`・`ops/metrics.py` の「守る数字の警告」）＞ 手順に書く（このファイル）＞ 決まりに書く（`CLAUDE.md`）。例：茨城の読み誤り（11/14）は、テストに加えて「同じ町・同じ時刻の発表が毎日続く」を警告にした（11/17）。
9. **報告する。** セッションの最後に、やったこと・PR・次に見る日を3行以内で書く。

## 4. 回す速さと、段階ごとの重点（2026-11-18・運営者の依頼で決めた）
速さは「結果が返ってくる速さ」に合わせる。返ってくる前に次を変えると、どれが効いたかわからなくなり、Google から見ても落ち着かないサイトになる。

| 仕事 | 結果が返る速さ | 回す速さ | 担当 |
|---|---|---|---|
| 火事の取り込み・公開 | 分 | 30分ごと（取り込みは5分ごと） | GitHub Actions・受付サーバー（AI は使わない） |
| 壊れたことに気づく | 分〜時間 | 毎回の生成・`gate` のメール | GitHub Actions（AI は使わない） |
| 有事の速さ・取り込みの改善（D） | 1〜3日 | 毎日の回 | AI |
| SEO の変更（登録・タイトル・内部リンク・noindex） | 1〜4週間 | **段階1・2のあいだは週1件まで**。前の変更の判定日（14日後）までは、同じ型のページに次の SEO の変更を重ねない | AI（週次の回で選ぶ） |
| 外を見る・仕組みの見直し | 週 | 週1回（月曜） | AI |

### 毎日の回でやること（段階1のあいだ）
1. 守る数字の警告・`gate` の失敗があれば、それだけを片付ける。
2. 判定日が来た実験を判定する。
3. 次のどれかを1つだけ選ぶ（上から優先。`docs/goals.md` の「PV を先に追う」）：
   - **PV を取るもの**：有事の速報の見せ方（大きな火事の速報まとめ・X 用の投稿文）／楽しめるコンテンツ（クイズ・診断）／注目の集まる読み物（今週の火事まとめ・季節の注意など）／共有されやすさ（共有ボタン・OG 画像）
   - D（掲載までの分数・読めない情報源）
   - 火事のページの固有の中身を増やす（E009）／検査・計測の穴
4. **やることがなければ、10分以内に「今日は変更なし」と報告して終える。** 変更を作るために変更を作らない。

### 速さを上げる合図
- 段階2（検索流入）に入り、1日の検索クリックが30を超えたら、毎日の回でも SEO の変更を選んでよい（週3件まで）。数字が返る速さが上がるため。
- 大きな火事でアクセスが跳ねた日（PV が前の7日平均の5倍以上）は、翌日の回で、その火事のページの見え方・回遊を最優先で見る。

## 3. 毎週の「外を見る」と週次レポート（月曜）
1. **外を調べる（自分たちでは思いつかない案を探す）。**
   - 海外・国内の似たサービス（例：米国の Citizen・PulsePoint・Watch Duty、防災アプリ、天気・災害の情報サイト）の新しい機能や伸び方
   - kaji.news の変化（利用規約で自動取得が禁止されているので、ページを数枚手で見る範囲にとどめる）
   - Search Console で、検索されているのに受け皿のない語句（`seo/gsc/api/queries_28d.csv`）
   - Google のガイドラインの変更（`seo/knowledge.md` を日付つきで更新する）
2. **案を5つ以上 backlog に足す。** それぞれに、参考にした事例か根拠、点数、自動か承認かを付ける。
3. **1週間の実験をふり返る。** 効かなかった型は `docs/experiments.md` の「わかったこと」に書く。
4. **仕組みそのものを見直す。** この手順や目標の改善案があれば、承認待ちの PR にする。
5. **週次レポート**を `ops/reports/weekly-YYYY-MM-DD.md` に書く。中身は次のとおり（運営者がスマホで1画面で読める長さ）。
   - 数字の推移（`ops/metrics/history.csv` の直近2週）と今の段階
   - 今週やったことと、効いた・効かなかったこと
   - 承認待ちの PR（番号・1行の説明・おすすめ）
   - 運営者にお願いしたいこと（3つまで。SNS の投稿なら文面まで用意する）
   - 来週の重点
6. 文書だけの PR にしてマージする。セッションの最後にレポートの要点を書く。

# 自動改善の手順（AI が毎日・毎週自分で回す）

運営者が 2026-11-12 に決めた仕組み。スケジュールタスクが新しいセッションでこのファイルを読み、書いてあるとおりに動く。
運営者は週1回のレポートを見て、まずいものだけ止める。**運営者への確認待ちで作業を止めない。** 承認が要るものは PR にして先へ進む。

## 0. 毎回の準備
1. リポジトリを最新にする（`git pull`）。
2. 次を読む：`CLAUDE.md` → `docs/STATUS.md` → `docs/goals.md` → `ops/metrics/latest.md` → `docs/experiments.md` → `docs/backlog.md`。
3. `ops/metrics/latest.md` の日付が今日でなければ、`python3 ops/metrics.py` を自分で動かす（Search Console の取得が止まっていれば、それも報告に書く）。

### 深く考える作業は Fable で
運営者の希望（2026-11-12）で、スケジュールタスクは Claude Fable で動かす。データの分析・仮説出し・外の調査など、深い情報処理が要る作業は、Agent ツールのサブエージェントを `model: "fable"` で呼んでよい。

## 1. 自動で進めてよい範囲と、承認が要る範囲

| 自動でマージしてよい | 承認が要る（PR を作り、タイトルの先頭に【承認待ち】を付けて止める） |
|---|---|
| バグの修正 | デザインの大きな変更（色・レイアウトの作り替え） |
| 収集元の追加・読み取りの改善 | 広告の場所・形式 |
| タイトル・説明文・内部リンクの改善（SEO 担当のルールに合うもの） | お金がかかるもの（有料の API・サービス） |
| 表示速度・生成の速さの改善 | 外部サービスへの登録・アカウント作成・SNS への投稿 |
| 検査・計測の追加 | データの削除、口コミ・報告の表示ルールの変更 |
| 文書（`docs/`・`ops/`）の更新 | 読み物の記事（画像は運営者が選ぶ決まりのため） |
| | `docs/goals.md`・`ops/goals.json`・このファイルの「自動でよい範囲」を広げる変更 |
| | `CLAUDE.md` の決まりと食い違う変更 |

迷ったら承認待ちにする。

### 上限
- 自動マージは1日1件まで。
- サイトマップに載るページを、1回の変更で100件以上増やさない。テンプレートの文言だけが違うページを大量に作らない（Google の「大量生成コンテンツ」の扱いを受ける危険がある）。
- 受付サーバー（`worker/`）の変更は、`worker/` のテストをすべて通したものだけ。

## 2. 毎日の改善（1日1回）
1. **守る数字を見る。** `ops/metrics/latest.md` の「守る数字の警告」があれば、その日は新しい改善をしない。原因を調べて直す。直近の自動マージが原因なら `git revert` の PR を作ってマージする。
2. **判定日が来た実験を判定する。** `docs/experiments.md` で判定日が今日以前のものを、書いてある数字で判定する。
   - 効いた → 結果を「採用」にする
   - 効かない・悪化した → 自動マージしたものは元に戻し、結果を「不採用」にして理由を書く
   - データが足りない → 判定日を1週間延ばす（延ばすのは2回まで。その後は「判定不能」）
   - 学んだことを「わかったこと」に1行足す
3. **今日やることを1つ選ぶ。** `docs/backlog.md` から、今の段階（または D）に効き、「自動」で、点数がいちばん高いものを選ぶ。
   - 良い候補がなければ、データから新しい仮説を3つ立てる。**1つは、これまでの実験と違う方向にする。** 点数を付けて backlog に足し、そこから選ぶ。
   - `docs/experiments.md` の「わかったこと」で効かないとわかった型は選ばない。
4. **小さく作る。** ブランチは `auto/YYYY-MM-DD-<短い名前>`。差分は300行くらいまで。
   - ページの追加・タイトルの変更・URL の変更は、`.claude/agents/seo.md` の判断ルールに照らす（SEO 担当のサブエージェントが使えれば呼ぶ）。
   - 手元の検査：`worker/` を触ったら `worker/*.test.mjs`。サイトを触ったら `cd site && python3 build.py`（生成）が通ることを確かめる。作業環境ではブラウザの検査（`verify.js`）が動かないことがあるので、ブラウザの検査は次の GitHub の `check` に任せる。
   - GitHub の検査：PR を作ると `check` ワークフロー（`.github/workflows/check.yml`。生成＋`verify.js`）が動く。1回20〜30分。結果は `gh api repos/nekolab0/kaji23/commits/<ブランチの最新コミット>/check-runs` で見る。不合格なら直す。直せなければ PR を閉じ、backlog にわけを書く。`.md`・`docs/`・`ops/`・`data/` だけの変更では `check` は動かない（それらは検査なしでよい）。
5. **出す。**
   - 自動の範囲：`check` が合格したら PR をマージする（`gh api -X PUT repos/nekolab0/kaji23/pulls/<番号>/merge -f merge_method=squash`）。マージで動く `daily` の公開が成功したかを確かめ、失敗したら元に戻す。セッションの残り時間で `check` が終わらないときは、PR を開いたままにし、翌日の回の最初にマージする。
   - 承認が要る：PR を作って止める。週次レポートに載せる。
6. **記録する（同じ PR に入れる）。**
   - `docs/experiments.md` に1行（何を・なぜ・どの数字がいつまでにどう動くはずか・判定日）。判定日は、インデックス・検索の数字なら14日後、速さ・件数なら3日後が目安。
   - `docs/backlog.md` の該当の行を「実施中」にする。
   - `docs/STATUS.md` を更新する。大きな判断は `docs/decisions.md` にも書く。
7. **報告する。** セッションの最後に、やったこと・PR・次に見る日を3行以内で書く。

## 3. 毎週の「外を見る」と週次レポート（月曜）
1. **外を調べる（自分たちでは思いつかない案を探す）。**
   - 海外・国内の似たサービス（例：米国の Citizen・PulsePoint・Watch Duty、防災アプリ、天気・災害の情報サイト）の新しい機能や伸び方
   - kaji.news の変化（利用規約で自動取得が禁止されているので、ページを数枚手で見る範囲にとどめる）
   - Search Console で、検索されているのに受け皿のない語句（`seo/gsc/api/queries_28d.csv`）
   - Google のガイドラインの変更（`seo/knowledge.md` を日付つきで更新する）
2. **案を5つ以上 backlog に足す。** それぞれに、参考にした事例か根拠、点数、自動か承認かを付ける。
3. **1週間の実験をふり返る。** 効かなかった型は `docs/experiments.md` の「わかったこと」に書く。
4. **仕組みそのものを見直す。** この手順や目標の改善案があれば、承認待ちの PR にする。
5. **週次レポート**を `ops/reports/weekly-YYYY-MM-DD.md` に書く。中身は次のとおり（運営者がスマホで1画面で読める長さ）。
   - 数字の推移（`ops/metrics/history.csv` の直近2週）と今の段階
   - 今週やったことと、効いた・効かなかったこと
   - 承認待ちの PR（番号・1行の説明・おすすめ）
   - 運営者にお願いしたいこと（3つまで。SNS の投稿なら文面まで用意する）
   - 来週の重点
6. 文書だけの PR にしてマージする。セッションの最後にレポートの要点を書く。

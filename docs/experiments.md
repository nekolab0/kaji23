## わかったこと
効いた型・効かなかった型を1行ずつ書く。次に何を選ぶかの判断に使う。

- 2026-11-22：「掲載件数が減った」は、件数の数字だけでは取りこぼしか火事が少ないかを分けられない。probe で今の検索を流し、「場所が読めない記事」の見出しを読むのが早い（大きな火事が、見出しに市区町村名がないだけで落ちていた。E013）。都道府県別に減った県（兵庫・大阪）だけを見ても原因はわからなかった
- 2026-11-21：報道の火事は毎回「直近48時間の記事」だけでまとめ直すので、最初の記事が検索結果から落ちると、残った続報の記事だけで別の日の火事ができる（E008 の公開時刻の固定では防げない型）。前の回の火事が使った記事は、ほかの火事に使わない（E012）。1回の取得で全部をまとめ直す仕組みでは、「前の回の結果」との食い違いを必ず確かめる
- 2026-11-21：外部 API の1件の失敗で、1日分の取得全体を捨てない。やり直しは1回、だめなら取れた分を保存して先へ進み、後ろの手順（数字のまとめ・保存）は止めない（`gsc.yml`・E012）

- 2026-11-20：「掲載件数が減った」（75.4→56.4件/日）は、取り込みの不具合ではなかった。①消防の発表：止まって見えた7ページ（鹿児島市・湖北・長崎県央・比企・上越・福山・上田）を `probe` で読み直したら、どれも読めていて読み取りも正しく、ページの最新の投稿が記録の最後の日付と同じだった（鹿児島市は 11/10 から投稿なし、長崎県央は「現在、火災情報はありません」）。②報道：11/18 までの二重取り込み（E008）が前の週に51件・直近の週に36件まじっていた。③前の日の分は翌朝の時点で2割ほど少なく、あとから増える。差し引くと、残りは実際の発表・報道の少なさ。警告が出たら、まず「ページ自体が投稿していないか」を probe（`collector/probe_pages.mjs` に、出動情報の一覧と同じ形で渡す）で見る
- 2026-11-19：仕組みの片方（worker の間引き・E007）を変えたら、それを見張る側（`verify.js` の監視）の前提も同時に変える。別々に書いた同じ数字（6時間・2時間）は食い違うので、関数を1つにしてテストで結ぶ（E011）。監視が毎回失敗すると、本当の異常のメールに気づけない

- 2026-11-17：同じ失敗を2度起こさないために、直したら検査を残す。茨城の読み誤り（E003）の型は、「同じ市区町村・同じ町名・同じ時刻の発表が直近14日で3日以上」で見つけられる（11/5〜11/14 のデータで13市町すべてが当たり、ほかは0件）。`ops/metrics.py` の「守る数字の警告」に入れた

- 2026-11-13：登録が進まないのは特定の型の問題ではない。調べた 2,598件のうち、Google が URL を知っているのはトップの1件だけで、6つの型すべてが同じ状態（E002 の最初の集計）。型ごとの題名や本文を直しても今は効かない見込み。効くのは、クロールを呼ぶこと（外からのリンク・サイトマップの読み込み）
- 2026-11-13：Google は、型ごとに分けたあと（PR #22・11/11）のサイトマップを2日たっても読みに来ていない。サイトマップの形を変えたら、Search Console での再送信までを1つの作業にする
- 2026-11-14：「掲載までの分数」の内訳（11/12〜11/13 にできた138ページ）。消防の発表のページは中央値36分・30分以内41%（誤りの26件を除いた34件）。報道のページは中央値154分・30分以内14%（78件）で、6時間を超えるものが32件ある。遅さの中心は報道の側
- 2026-11-14：報道の「6時間超」には、測り方のせいで遅く見えるものが混じる。あとから町名がわかった・消防の発表のページが報道のページにまとまった、でファイル名が変わると、できた時刻だけが新しくなる（同じ情報源時刻のページの組を6組確認。例：小矢部市は最初のページが217分、町名つきに変わったあとのページは1,117分と数えていた）。本当に遅い分がどれだけあるかは、測り方を直すまで不明

# 火事速の目標（自動改善の判断基準）

運営者が 2026-11-12 に決めた目標。AI の自動改善（`docs/autopilot.md`）は、この目標に効くかどうかで何をするかを決める。
数字は `ops/goals.json` にも同じものを置き、`ops/metrics.py` が毎朝 `ops/metrics/latest.md` に今日の値と今の段階を書く。
**合格ラインや段階の中身を変えるのは、運営者の承認が必要。**

## 最終目標
**月間PV（広告収益）。** 順位・表示回数・件数は手段。

## A. 段階（今のボトルネックの数字だけを追う）
合格ラインを越えたら、次の段階に自動で進む。合格ラインは仮の値で、3か月ごとに見直す。

| 段階 | 追う数字 | 合格ライン（仮） | 見る場所 |
|---|---|---|---|
| 1. インデックス | Google に登録されたページ数 | 1,000ページ | Search Console の URL 検査（`seo/gsc/api/meta.json`） |
| 2. 検索流入 | 検索からのクリック（直近7日の1日平均） | 100クリック/日 | `seo/gsc/api/by_date.csv` |
| 3. 回遊 | 1訪問あたりのページ数（直近7日） | 1.8ページ | Cloudflare Web Analytics（`ops/analytics/latest.json`） |
| 4. 収益 | 1,000PV あたりの広告収益 | 未定 | AdSense（まだ取得していない） |

- 改善の8割は今の段階の数字に向ける。残りの2割は次の段階の準備と D に使う。
- 段階1のあいだは、ページを増やすより登録の対策を先にする（`docs/STATUS.md` の方針と同じ）。

## D. 有事の速さ（段階に関係なく、いつも追う）
火事のアクセスは、大きな火事が起きた瞬間に跳ねる。そのときに最初に載っているサイトが勝つ。

- 追う数字：**情報源の時刻（報道の配信・消防の発表）から、火事のページができるまでの分数**（直近7日の中央値）
- 目標：中央値30分以内
- 測り方：`site/build.py` の `fire_first_seen` が `data/raw/fire_first_seen.json` に残す時刻から、`ops/metrics.py` が計算する。2026-11-12 に計測を始めたので、それより前のページは「不明」
- 段階2に入ったら、「〇〇 火事」の検索での火事のページの順位も追う

## 守る数字（悪化したら、その変更を元に戻す）
- 検査（`verify/report.json`）の error 級がすべて合格
- 掲載件数（報道＋消防の発表）の7日平均が、前の7日より20%以上減らない
- 誤った情報・削除依頼が0件
- 表示速度を落とさない（ページの重さを大きく増やさない）
